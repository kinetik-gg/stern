# Design system primitives map

This is a conformance inventory, not a design proposal. It maps the design
system's 13 behavior primitives and 23 shared data contracts
(`../stern-design-system/src/behaviors/primitives-and-contracts.md`, read
2026-08-03) onto stern's actual Rust implementation. It exists because
STERN-PRIM-001 requires components to compose canonical behavior primitives
instead of private state machines, and nobody had checked whether stern's
`crates/stern-core/src/interaction/` module and the rest of the workspace
actually line up with the design system's vocabulary. No behavior changed to
produce this document; every citation below was read directly from the tree.

The design-system source document is explicit that it "does not prescribe
Rust type names or move application policy into widgets." A stern type
having a different name than its DS primitive is not itself a gap. A stern
type having different *ownership*, *emitted events*, or a different
*cancellation invariant* than its DS primitive is a gap, and those are
tracked in `KNOWN-GAPS.md`, not silently noted here.

Workspace crates consulted: `stern-core`, `stern-widgets`, `stern-text`
(from the repo-root `Cargo.toml`). Neutral primitives live in
`crates/stern-core/src/interaction/` (module root:
`crates/stern-core/src/interaction.rs:1-51`, 8 files: `press.rs`,
`drag_select.rs`, `focus.rs`, `scroll.rs`, `overlay.rs`, `hit.rs`,
`response.rs`, `tests.rs`). Domain-specific composites live in
`stern-widgets`; retained text state lives in `stern-text`.

## Summary

- **Primitives:** 9 of 13 have literally-named, directly comparable stern
  implementations in `stern-core::interaction` (`pressable`, `selectable`,
  `draggable`, `focusable`, `scrollable`, `text_editable`, `drop_target`,
  `tooltip_trigger`, `context_menu_trigger`). 4 of 13
  (`value_transaction`, `roving_focus`, `anchored_surface`,
  `two_axis_value`) have no literal stern vocabulary and live in
  `stern-widgets` under different names; of those, `anchored_surface` is a
  strong functional match, `value_transaction` and `roving_focus` have
  genuine parity gaps tracked in `KNOWN-GAPS.md`, and `two_axis_value` is
  effectively absent as a joint primitive.
- **Contracts:** 21 of 23 are fully represented. `multi-value-state` is a
  bare boolean flag instead of a generic value wrapper, and
  `platform-window-policy` is three distributed mechanisms instead of one
  declarative type; both are noted above, only the former is tracked as a
  `KNOWN-GAPS.md` item since it is the one with a concrete missing-capability
  story (multi-selection property editing).
